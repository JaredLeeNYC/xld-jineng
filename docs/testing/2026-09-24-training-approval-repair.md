# 培训补录计划审批修复方案与验证

## 问题与原因

线上以生产部主管审批 HR 提交的《精益生产培训》时，接口返回 HTTP 409、`PLAN_APPROVAL_REJECTED`。该计划仍为待审批，没有生成培训任务或履历。

审批逻辑错误复用了“新建计划时可选择的资料”查询。HR 上传、未关联技能的资料可以随待审批计划被负责人查看，但不满足主管新建计划的资料选择条件，因此审批被拒绝。错误提示将资料、管理范围和自审批混在一起，无法直接区分原因。

## 已实施修复

1. 审批时检查计划既有资料是否存在、启用且未归档，不再套用新建计划的资料选择权限。
2. 保留负责人、全部培训对象及部门管理范围校验，保留禁止创建人或提交人自审批的规则。
3. 将失败提示细分为计划状态、自审批、资料失效和管理范围问题。
4. 新建或编辑草稿的资料选择权限保持原有规则。

本次不改数据库结构，不需要修改生产业务记录或补造审批结果。部署后，符合条件的待审批计划可直接重新审批。

行政部也适用上述规则；若审批账号正是创建人或提交人，仍需由另一位具有相应权限的人员审批，不能通过本次修复绕过独立审批。

## 验证结果

- `bun run check` 通过，包括代码检查、类型检查、接口与部署契约、真实 PostgreSQL 契约测试和前端构建。
- 全量 `bun test`：156 项通过，0 项失败，518 个断言。
- PostgreSQL 新增回归覆盖 HR 无技能关联资料、本部门主管审批、跨部门拒绝、自审批拒绝、停用和归档资料拒绝、补录履历和实际起止时间、重复审批拒绝。
- 拒绝审批后验证计划仍待审批且没有生成任务。
- 验证修复没有扩大主管新建草稿的资料选择权限。

## 发布与线上验证步骤

1. 按现有发布流程发布包含本次修改的服务端版本；本次无需数据迁移或批量数据修复。
2. 使用对应部门主管账号重新打开待审批计划，核对资料、负责人和参训员工。
3. 对已授权的《精益生产培训》执行审批，确认成功，补录计划转为已完成，生成四名参训员工对应的履历及实际培训时间。
4. 对其他部门按相同条件抽查；如仍失败，依据新的具体提示处理资料有效性、部门范围或独立审批问题。
5. 如需回退，回退应用版本；已经正常生成的正式培训任务和履历保留，不物理删除。

前两轮发布在既有全厂只读授权脚本中因仅按姓名匹配账号而失败。本次按用户明确提供的工号 `10032` 和姓名共同定位，保留有效状态、角色、唯一性及幂等检查；不扩大原定授权范围。真实 PostgreSQL 契约覆盖姓名相同但工号不符时拒绝授权，以及精确匹配后授权、重复执行和角色保持。
